0.5.0 adds [Hermes](https://github.com/NousResearch/hermes-agent): the same guard, the same rules and the same config keys, as a Hermes plugin from this repo. Pi is unchanged: the same decisions and the same messages.

**One core, two hosts.** The decision pipeline moved out of `index.ts` into [`core/`](core/): the config, the scorers, the chat decider, the pipeline itself, and the wording both status commands use. `core/`, `rules.ts` and `automode.ts` import nothing from Pi. What Pi alone knows stays in `index.ts`: its events, its config file, its prompt, its model registry. What Hermes alone knows is in [`hermes/`](hermes/): the hooks, the tool map, the endpoints, and the session text.

**A Hermes call goes through the same stages.** Hermes runs Python and the guard is TypeScript, so the plugin registers `pre_tool_call`, `pre_llm_call` and `post_tool_call`, and starts `hermes/hook.ts` with a Node that runs TypeScript, one process per call: JSON in, one of allow, block, or escalate to Hermes' approval gate out. Rules, scorers and chat decider are the ones described in the README, and their reasons name Hermes where Pi's name them Pi. Stage 1 alone costs about 85 ms per call on my machine, most of it Node starting.

**It fails closed.** No Node, a guard that is late, an answer that is unreadable, an answer the wrapper does not know, a chat model that cannot be reached: all of them go to the approval gate, and Hermes denies an approval nobody answers. In a session with nobody to answer (cron, a kanban worker, `webhook`, `api_server`) the config's `withoutUi.onAsk` decides, as in print mode on Pi.

**Each profile gets its own config and log**: `<profile home>/automode-classifier/config.json` and `decisions.jsonl` beside it. `/automode-classifier status`, `on` and `off` work there too, with the same rows as Pi, the session counts included.

**One session's state survives the process it started in.** A Hermes decision runs in a fresh Node process, so what the session knew would be lost: which files it wrote or downloaded, the counts `status` prints, and the denial counts. They now live in `<profile home>/automode-classifier/sessions/<session id>.json`. It is the same state Pi keeps in memory, read and written by `core/session.ts`: a save merges the change each call made, under a lock file, because two calls of one session can run at once, and a session idle for 7 days is deleted. So a script the session downloaded asks before it runs, one it wrote goes to the chat decider, and `maxConsecutiveDenials` and `maxTotalDenials` escalate to a person after the run of denials they name. With `llm.warmCache` on, the first hook of a session starts the throwaway chat call in a process of its own and does not wait for it, so no turn pays the cold prefill.

**Every Hermes call that runs a command or writes a file is judged by what it really touches.** A `patch` in V4A mode is judged by every file its `*** Add/Update/Delete/Move File:` lines name, and a patch text the guard cannot read asks. The `workdir` of a `terminal` call is judged as the `cd` it is, so a folder outside the project does not become the project. Text that `process_manage` sends to a running shell or REPL (`write`, `submit`) is judged as a command. Every profile's guard config, plugin copy, `config.yaml`, `.env` and `SOUL.md` are locked, and its `skills`, `memories`, `scripts` and hooks folders count as Hermes' own files. An approval a person gives in Hermes covers that call only while it stays as safe as it was: once a file it runs has been downloaded over, the call asks again.

**Three Hermes tools that reach a command or a file without naming it are judged now**: the `script` a `cronjob_manage` job will run later, a `skill_manage` write in the profile's skills folder, and a `memory` note in its memories folder. `delegate_task` needs nothing: Hermes runs each child through the same loop that fires `pre_tool_call`, so a child's calls are judged on their own. The README lists all 67 built-in tools and what the guard does with each.

**A new key, `providers`,** names the endpoints a Hermes config uses, because Hermes hands a plugin no handle on the session's model:

```json
{
  "decider": ["classifier", "llm"],
  "classifier": { "provider": "z13", "model": "lancet" },
  "llm": { "provider": "z13", "model": "flash-next-128k", "contextWindow": 131072, "thinkingLevel": "off" },
  "providers": { "z13": { "baseUrl": "http://z13.local:11435/v1", "apiKeyEnv": "LLAMASTASH_KEY" } }
}
```

The plugin reads the key through Hermes' own secret lookup, with the environment behind it. Stage 2 posts to `<baseUrl>/systemone`, stage 3 to `<baseUrl>/chat/completions`. Set `llm.contextWindow` to what the endpoint has: the rule prompt is about 25,000 tokens, and a smaller window holds every call back as "too small to classify". Set `plugins.hook_callback_timeout` above the wait the stages need, or Hermes abandons the callback and blocks the tool with a timeout message. Hermes' own installer refuses it, because its scanner reads the plugin's rule list as a list of dangerous commands and `--force` does not override that, so a Hermes install is a clone into the profile's plugin folder and a `git pull` to update. [Hermes agents](https://github.com/deepu105/pi-automode-classifier#hermes-agents) has the install, the mapping table and the limits.

**Two things from the Pi plugin have no Hermes equivalent**, and the README lists them: the prompt's wider choices (`Always allow "git push *"`, saved to your config) and `promptTimeoutMs`. Hermes answers an approval one call at a time and a plugin never learns what the person chose, so nothing wider is offered; put those patterns in the profile's `rules.allow` and `allowedPaths` instead.

**Hermes cannot update this plugin**, because the same scanner that refuses `hermes plugins install` refuses `hermes plugins update`: on 0.23.3 `adopt` and `check-updates` work on a cloned plugin and `update` answers "Blocked (community source + dangerous verdict, 105 findings). --force does not override a dangerous verdict". So the update path is git: pull the clone and restart the gateway, or run an installer that does that. The source is the same repository Pi installs from.

**The suite grew.** `npm test` now runs three suites: `test.mjs` (rules, config, Pi handler), `test-hermes.mjs` (the wrapper's TypeScript: tool map, session text, endpoint requests, the JSON answers, both fail-closed paths) and `test_hermes.py` (the Python half against a fake Hermes ctx). None needs a model, a server, or a Hermes install. CI runs `npm test` on Node 22 and 24 instead of `node test.mjs`.
