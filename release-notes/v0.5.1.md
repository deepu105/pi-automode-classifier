0.5.1 adds one config key, `credentialPaths`: your own files and directories that count as credential files. A read of one gets the same firm ask as a built-in credential file, in Pi and in Hermes.

```json
{ "credentialPaths": ["~/work/vaults", "~/.config/mytool/token"] }
```

An entry is an absolute path or starts with `~/`. A directory entry covers everything under it, and a symlink counts as the path it points at, in the entry and in the path read. The same three tools are covered as before: a shell command that reads the file, and the `read` and `grep` tools. An input redirect counts as a read too, so `tee /tmp/out < ~/work/vaults/token.dat` now asks. The same fix covers the built-in files: `tee /tmp/out < ~/.ssh/id_rsa` ran before. Two more reads now ask, for a listed path and for the built-in files alike: a `file://` URL (`curl file:///home/me/.ssh/id_rsa`), and a file that `$(< file)` hands out with no command in front of it (`echo $(< ~/.ssh/id_rsa)`).

A listed path counts inside a word too, so a path with a space (`cat "~/my vaults/token.dat"`) and a path inside inline code (`python -c "open('/home/me/work/vaults/token.dat')"`) ask. It matches only at a path boundary: `~/work/vaults` does not match `~/work/vaults2`. Text that only names the path does not ask, so `git commit -m "notes moved out of ~/work/vaults"` and `bash -c "ls -la ~/work/vaults"` run.

What still runs is what still runs for a built-in credential file: a command that only names the file (`ls`, `stat`, `test -f`, `chmod`), a write to it, and anything your own `allow` rule covers.

The key is validated like every other key. An entry that is not text, is empty, is a relative path, or starts with `~user` ignores the config as a whole and names the problem, so a typo cannot half-apply.
